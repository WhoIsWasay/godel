        <step number="2.5" title="IDENTIFY STATE PRECONDITIONS (CRITICAL)">
            For EVERY finding from step 2, you MUST answer these questions before generating any Z3 code:

            Q1: "What contract state must be true for this bug to trigger?"
                - A floor-division bug only matters when the denominator is disproportionately large relative to the numerator.
                - A ratio calculation bug only triggers when one side of the ratio has been inflated/deflated by external action.
                - An underflow only occurs when a variable has been mutated into an unexpected range.

            Q2: "What adversary action or sequence of events can create that state?"
                - Direct token donation to the contract (inflates balance without minting shares)
                - Flash loan that temporarily inflates/deflates a balance
                - First-depositor attack (totalSupply is very small relative to deposited assets)
                - Fee accrual or yield accumulation that inflates one side of a ratio
                - Time passage that changes a rate or accumulator

            Q3: "What is the MINIMUM Z3 constraint that encodes this adversarial state?"
                - You MUST include the precondition in your solver. A property that checks `amount > 0 => shares > 0` is USELESS if the real bug only triggers when `totalAssets > totalSupply * 1000`. You MUST add that precondition.

            ENCODING RULE: Every Z3 property MUST include at least one state precondition constraint.
            Template: `s.add(precondition_constraint)  # adversarial state that triggers the bug`

            EXAMPLE (donation attack on share minting):
                Finding: "floor division in share calculation can mint zero shares"
                Precondition: totalAssets is disproportionately large relative to totalSupply
                Z3 encoding: `s.add(UGT(totalAssets, UMul(totalSupply, BitVecVal(100, 256))))  # donation inflated assets`
                Then check: `s.add(And(UGT(depositAmount, 0), shares == 0))`

            EXAMPLE (ratio manipulation):
                Finding: "reward calculation uses stale denominator"
                Precondition: denominator was updated BEFORE numerator (dilution attack)
                Z3 encoding: `s.add(UGT(totalSupply_1, totalSupply_0))  # supply inflated before rate update`
                Then check: `s.add(ULT(rewardPerToken_1, rewardPerToken_0))`

            If you skip this step, your property will be too weak and Z3 will return UNSAT on a trivially-safe model — a FALSE NEGATIVE that lets real bugs through.
        </step>

        <step number="4" title="ENCODE THE PROPERTY">
            Negate the property. You are searching for a counterexample — a state where the invariant is violated. If Z3 returns SAT, a bug exists. If UNSAT, the property holds under your model.

            CRITICAL RULE: Your negated property MUST include the state preconditions from step 2.5.
            - WRONG: `s.add(And(amount > 0, shares == 0))` — too generic, Z3 returns UNSAT because this is safe under normal conditions

            ANTI-FALSE-NEGATIVE PROTOCOL:

            1. Normal state (baseline — should be UNSAT, confirms your model is correct)
            2. Donation-inflated state (totalAssets >> totalSupply)
            3. First-depositor state (totalSupply = 1, totalAssets very large)
            4. Dust-amount state (amount = 1, denominator very large)

            Implementation: use solver.push()/solver.pop() to test multiple scenarios:
            ```

            s.push()
            s.add(UGT(totalAssets, UMul(totalSupply, BitVecVal(1000, 256))))
            s.add(And(UGT(amount, 0), shares == 0))
            if s.check() == sat:
                print("BUG FOUND (donation attack):", s.model())
            s.pop()

            # Scenario 2: first depositor
            s.push()
            s.add(totalSupply == BitVecVal(1, 256))
            s.add(UGT(totalAssets, BitVecVal(100000, 256)))
            s.add(And(UGT(amount, 0), shares == 0))
            if s.check() == sat:
                print("BUG FOUND (first depositor):", s.model())
            s.pop()
            ```

        <step number="5" title="ENCODE EDGE CASES FROM FINDINGS">
            Add explicit constraints derived from the findings. Common patterns to check for:
            - Zero supply / zero balance states
            - Overflow boundaries (uint96 max, uint256 max)
            - Fee/reward accumulation that inflates or deflates balances
            - Stale ratio calculations (shares * pool / totalShares patterns)
            - Oracle/price manipulation: if the target function reads an external price/oracle value once and uses it directly in a critical calculation (liquidation, valuation, collateral check) with no staleness check, TWAP, or bounds validation, treat that price as adversarially controlled. Model it as a free Int variable constrained only to a plausible numeric range (e.g. 0 to 10**6), and check whether extreme values (very low or very high) can flip the invariant — e.g. force a healthy position to appear liquidatable, or an unhealthy one to appear safe.
            - Share/ratio inflation: if the target function computes a share or token amount using a ratio like (amount * totalX) / totalY, explicitly test the edge case where totalY is disproportionately large relative to amount * totalX (simulating a direct "donation" attack that inflates totalY without minting proportional shares). Check whether the result can round down to zero for a legitimate depositor with amount > 0.
            - Floor division truncation: if the function uses integer division (e.g., shares = (tokens * SCALE) / price), you MUST encode the truncation behavior. In Z3, this means: `shares = UDiv(tokens * SCALE, price)`. Then assert: `And(tokens > 0, shares == 0)` to check if a positive input can produce zero output. This is a critical bug pattern in yield-bearing vaults where high share prices cause new depositors to receive zero shares.
            - Wrong variable passed to external call: if a function converts between units (e.g., amount→shares or shares→amount) and then passes the converted value to an external function that expects the original unit, model this mismatch. For example, if `redeemAmount` is converted to `shares` but `shares` is passed to `externalRedeem(redeemAmount)`, the external call receives the wrong denomination. Encode the property: the value passed to the external call must equal the user's requested amount, not the converted intermediate.
        </step>
        <step number="5.5" title="EVM ARITHMETIC LAW">
        When executing mathematical operators over BitVec variables, you must explicitly enforce unsigned EVM semantics:
        - Division must strictly use UDiv(a, b) instead of regular python division (/).
        - Modulo/Remainder operations must strictly use URem(a, b) instead of regular python remainder (%).
        - Unsigned comparison operators must use ULT(a, b) for <, ULE(a, b) for <=, UGT(a, b) for >, and UGE(a, b) for >=.
        - To check for an explicit 0.8+ arithmetic overflow revert condition on addition, assert: Not(UGE(a + b, a)). If this evaluates to True, an EVM overflow occurred.
